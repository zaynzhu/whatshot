# 筛选与首播日期时间轴：豆瓣补充调研

> 调研时间：2026-09-12 至 2026-09-13。
> 状态：调研讨论稿。剧集时间线按首播日期倒序的产品目标已明确；未批准接入豆瓣或启动开发，应用排序尚未修改。
> 本文承接用户提供的调研交接及随后的口径澄清；既有需求仍以 [requirements.md](requirements.md) 为准。

## 1. 用户澄清后的目标

用户确认所指信息是豆瓣作品主页上的 **“首播：2026-08-31(中国大陆)”**，并不要求获取第一集或逐集播出日程。

因此，交接稿中“用户看到分集区有逐集播出日程”的前提不成立，停止追查逐集接口。用户进一步明确：整体剧集时间线按首播日期排序，后续集数更新不应使它排到前面。

**已确认的产品定义：新剧／老剧按整部剧的首播先后区分，剧集时间线按首播日期倒序。** 以用户给出的 9 月 12 日为示例观察日，顺序是 9 月 12 日首播、9 月 11 日首播、9 月 10 日首播，依此向前；这里的日期是示例，不将其当作调研当天日期。

后续增加集数、重新供种、重新入库或评分变化均不应改变首播日期排序位置。这个目标与此前“默认保持资源更新时间排序”的候选方案发生了变化，后续需求定稿应采用用户这次的最新口径。它不构成现在开始编码或接入外部来源的授权。

三种日期对应不同问题：

| 日期口径 | 回答的问题 | 《飞到我心上》的表现 |
|----------|------------|----------------------|
| 首播日期 | 哪些剧最近开播 | 归到 2026-08-31；后续更新集数不改变此日期 |
| 最近一集播出日期 | 哪些剧最近播了新一集 | 需要逐集日程；本次不再追查 |
| 集数更新观察日期 | 应用最近发现哪些剧集数增加 | 随成功观察变化，但不等于真实播出日 |

“9 月 12 日开播的剧在 9 月 11 日开播的剧前面”可由首播日期排序实现；“9 月 12 日更新了一集的剧排前面”是另一项需求，不能宣称首播日期排序同时满足。

## 2. 本次采用与补充验证的边界

直接沿用用户交接中的 butai0 筛选参数、release 覆盖不足、tvMaze 对已测国产剧不可用、豆瓣单条 pubdate 可得等结论，没有重复调研这些事实。

本次补充工作：

- 只读查询本地 videos 的作品身份、地区、类型与状态，为覆盖评估选取条目；SQLite 使用 mode=ro 和 query_only。
- 使用现有豆瓣 ID，对另外 10 部国产在更新条目请求豆瓣详情，检查标题与 pubdate；不通过标题搜索寻找身份。
- 澄清前检查了豆瓣分集页面与一个分页 episodes 请求；澄清后停止此路线。
- 未写入业务库，未触发 WhatShot 同步，未读取或复制登录 Cookie、代理值和用户浏览记录。
- 浏览器只使用本次新建页面，网络捕获已停止，本次 session 已关闭。

检索工具方面：Tavily 本次出现 TLS EOF 错误，已明确说明后改用备用网页搜索。搜索结果没有提供可用技术证据，本文结论来自豆瓣实际响应与页面、只读本地样本。

## 4. 可复现的首播日期请求

下面与本次成功请求采用同一 URL、UA 与 Referer，不需要 Cookie、Token 或 API Key：

```bash
curl -sS --max-time 18 \
  -A 'Mozilla/5.0 (iPhone; CPU iPhone OS 17_0 like Mac OS X) AppleWebKit/605.1.15 Mobile/15E148' \
  -H 'Referer: https://m.douban.com/tv/36314809/' \
  'https://m.douban.com/rexxar/api/v2/tv/36314809' \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); print(json.dumps({"title":d.get("title"),"pubdate":d.get("pubdate")},ensure_ascii=False))'
```

本次结果：

```json
{"title": "交锋", "pubdate": ["2026-09-06(中国大陆)"]}
```

该命令用于单例人工复现，不是生产解析器；执行多次时，必须统一串行控制请求间隔至少 2 秒。本次样本每次请求前等待 2.2 秒，且响应结束后才进入下一条，没有并发轰击。

本次 10 个样本均由 /tv/ 路径成功返回。其他条目的 kind 选择、电影范围覆盖，本次没有新增验证；不能根据网页域名 movie.douban.com 判断 rexxar 的 movie/tv 类型。

## 5. 分集路线的已知结果与停止原因

这部分仅保存本次已发生的验证，避免以后把猜测当成可用接口。逐集日程已不是澄清后的目标。

### 分页参数未使候选接口可用

```bash
curl -sS --max-time 25 \
  -A 'Mozilla/5.0 (iPhone; CPU iPhone OS 17_0 like Mac OS X) AppleWebKit/605.1.15 Mobile/15E148' \
  -H 'Referer: https://m.douban.com/tv/37172262/' \
  -w '\nHTTP_STATUS=%{http_code}\n' \
  'https://m.douban.com/rexxar/api/v2/tv/37172262/episodes?start=0&count=50'
```

本次返回 HTTP 404、msg=traversal_error、code=404，含义为要访问的内容不存在。它不是可用于推导“共 0 集”的正常空分页结果。这个请求没有证明更换参数、登录或其他端点一定可行，也不能证明豆瓣所有分集接口均不存在。

### 原生分集页面存在，但已读样本没有播放日期

- [《飞到我心上》第 1 集](https://movie.douban.com/subject/37172262/episode/1/)：浏览器返回正常页面，.ep-info 内“播放时间”为“暂无，欢迎添加”。它说明有字段结构，不说明有日期覆盖。
- 第 21 集：无 Cookie 的 curl 跟随重定向后进入 sec.douban.com；浏览器正常导航也进入相同安全页面，遂停止。最终 HTTP 200 来自安全页，不能当作内容请求成功。
- 原计划扩大的分集样本没有执行完成，因此没有分集日期批量覆盖率，不能报告 0% 或 100%。

为寻找日程字段查看的同一作品 rexxar 详情中，episodes_info 为“更新至14集”，last_episode_number、pre_playable_date、release_date 均为 null。episodes_info 是进度文本，不是逐集日期表；也不能与 butai0 的进度强行合并为同一时间口径。

## 6. 工程成本与边界评估

### 限频和可用性

- 本次 10 个详情请求在串行、每次间隔超过 2 秒的条件下全部成功，无需登录。
- 这只能证明本次低频短批次可用。未测试限流阈值、IP 封禁阈值或长期稳定性；不以探测封禁阈值为目标加压。
- 网页分集路线已遇到安全重定向。详情 JSON 路线与网页访问的表现应分开记录，不能用一方结果保证另一方。
- 若以后接入，豆瓣各端点应共享同一限频器，至少 2 秒间隔、低并发；不把 /movie/ 和 /tv/ 当成两个独立额度。
- 遇到 429 尊重 Retry-After，401/403 或安全验证页停止该批次并退避；不自动索取登录 Cookie，不换 IP 或循环改参数绕过限制。

### 请求预算

首播日通常不随每次集数更新变化，因此无需每 6 小时对全部条目重新抓取。若未来批准，可在现有同步周期内，以受限补全预算处理首次缺失及到期重查，并保留日期修正的可能性；不改变主同步周期和活跃内容范围。

按 2 秒的最小请求起始间隔估算，125 个串行请求从第一条到最后一条开始，至少需 248 秒，还未计完整响应耗时。不能把“单个接口好接”写成“整批补全免费”。这个数字是请求预算估算，本次没有抓取全部 125 条。

### 失败降级

候选方案应确保：豆瓣失败不阻断 butai0 同步、不清空已有首播日、不导致列表不可用。没有日期的条目显示“首播日期未知”，不能偷偷用资源更新时间或观察时间填充成真实首播日期。

首播日排序目标已经明确，但未知日期的安置规则尚未定稿；未来日期应与已播内容的冲突单独处理，不能将其顶到已播时间轴最前。建议未知日期单列或置后、同日使用稳定次序，这些边缘交互仍待确定。

### 数据语义与本地边界

- pubdate 是数组，可能包含不同地区和不同日期精度。只把真实存在的完整 YYYY-MM-DD 当成日级日期，不把仅年份补成 1 月 1 日。
- 国产剧样本可取明确标记中国大陆的首播日期；其他地区、多次播出或版本差异如何选择，需要独立规则。本次未验证全球日期覆盖。
- 首播日按自然日保存，不能先擅自假设 UTC 午夜再转时区，造成前后一天偏移。
- 补充日期、来源和抓取时间只落本地 SQLite，不新增后端或上传库。
- “只存本地”不等于没有外发：向豆瓣请求指定条目会让豆瓣看到该条目 ID 和客户端网络信息。不得额外发送本地偏好、完整资料库、域名与代理设置。
- 无需把评分、简介、全部外部详情、响应 Cookie 等与本目标无关的数据持久化。

### 一期单源边界：必须由用户决定

如果应用直接请求豆瓣，它在技术上就增加了第二个来源，即使只补一个日期字段也一样。

两种可讨论定位：

1. 一期的明确例外：主数据仍来自 butai0，只允许豆瓣按已有 ID 补首播日期，范围写清楚。
2. 二期的首个受限外部元数据来源：明确承认多源，但不意味着同时开发多源热度、推荐或 NAS。

本次不替用户选择，也不把研究请求视为生产接入批准。

## 7. 不新增来源时的替代与代价

在只使用现有本地字段的前提下，没有已验证的方法凭空恢复缺失的真实首播日。

| 选项 | 能解决什么 | 不能解决什么 |
|------|------------|--------------|
| 已批准方向的本地年代、状态、类型、地区筛选 | 缩小当前资源更新列表，减少老剧干扰 | 没有日级首播时间轴；年份有错误的可能 |
| 本地集数变化观察 | 呈现确实观察到的集数推进 | 不能恢复真实首播日、真实逐集播出日 |
| 用户手动补首播日并注明来源 | 少量重点作品获得明确日期，不增加自动外部抓取 | 需要持续人工维护；仍是一项尚未批准的新功能 |

观察日方案还需注意：首次入库不是新播出；首次看到“全集”不是今天完结；历史裁剪后的最早记录不是实际更新日；补齐旧集或数据修正也可能形成变化。6 小时只是正常在线条件下的同步间隔，资源上站延迟、休眠、关机和失败会使误差更大，不能承诺“最多半天”。

## 8. 结论与当前状态

1. 用户实际指向的是整部剧的首播日期，逐集日程不是继续调查的前提。
2. 豆瓣 pubdate 对本次新增的 10 部国产在更新样本全部可得，值得讨论一个范围很窄的日期补全方案；暂无依据保证全库和长期可用性。
3. 年代筛选可以作为辅助，但用户的核心目标已明确为剧集按首播日期倒序。集数增加和重新供种不能使老剧冒头；当前应用尚未改动。
4. 接入豆瓣是一期例外还是二期能力，仍待用户拍板；排序目标不再是开放问题，同日顺序、未知及未来日期展示等细节尚未定稿。
5. 本次交付只有调研文档；未改应用、正式需求或业务数据。
