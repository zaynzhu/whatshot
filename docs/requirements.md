## 项目定位

WhatShot 聚焦**已播出影视的热度与播出进度**：

- 核心问题一：某部剧/电影现在热不热（热门榜、资源数、评分）
- 核心问题二：某部剧现在更新到第几集（更新至 X 集 / 共 Y 集 / 全集完结）
- 一期不做：资源搜索接入（二期）
- 交付形态：类似 WhatsNew 的 macOS 应用（dmg 本地打包，不做签名公证）

参考项目 WhatsNew（`../whatsnew`）只作为架构与规范参考，不作为代码基底，**不得改动**。

## 参考站 butai0.club 调研结论（2026-09-11 实测）

### 站点性质

- Vue SPA，HTML 是空壳，数据全部来自 JSON 接口
- 无需登录即可获取核心数据；种子/网盘**列表**需 VIP（`need_vip:1`），但卡片级数据不受影响
- 站点自身声明了多个备用域名（butailing.com、0bt0~9bt0.com 等），**域名会变，必须可配置**
- **域名池自动择优（2026-09-12 定案，2026-09-13 升级为发布页自动发现）**：官方域名（butai0.club/com/dev/one/vip/xyz、0bt0~9bt0.com，共 16 个，同库不同 CDN 路由，接口内容逐条一致——切换域名零数据风险）。**每次同步前抓发布页 https://www.butailing.com/ 的 HOSTS 数组自动发现官方域名**（站点换域名家族不再需要改代码）；发布页不可达时静默回落内置兜底池（`DomainPool.swift` 的 `fallbackDomains`，2026-09-13 与发布页同步确认）。用户自定义地址恒为最高优先，探活走真实 API 路径 HEAD（冠军记忆：先探上次成功的域名，通了只花一次探活；失败才全池并行取最快）；同步中同域名连续 2 次失败自动降级换域名从失败步骤继续，全池不可达才报错。发布页解析只收 HOSTS 数组区间内的域名，解析失败/无结果一律回落兜底池不报错

### 公开 JSON 接口

基址：`https://www.butai0.club/prod/api/v1/`
公开参数：`app_id=83768d9ad4`、`identity=23734adac0301bccdcb107c4aa21f96c`（写死在前端 JS 的固定值，缺失时报 `接口鉴权失败` code 10101）

| 接口 | 用途 | 关键字段 |
|------|------|---------|
| `getVideoList?sc=1/2` | 首页电影/电视剧精选 | 同热门榜 |
| `getVideoList?sc=3/4/5` | 近日/本周/本月热门榜，各 35 条 | `title`、`ejs`、`episodes`、`seed_num`、`wp_num`、`doub_score`、`doub_id`、`IMDB_number`、`IMDB_score`、`definition`、`class`、`production_area`、`years`、`release`、`abstract`、`director`、`performer`、`seed_updated_at`、`updated_at` |
| `getVideoMovieList?sa=1(电影)/2(剧集)&page=N` | 全库列表，total 25124 条，每页 25 条；支持类型/地区/年份/画质/状态(更新中/已完结)/排序(更新时间等)筛选 | 列表版字段：`doub_id`、`id`(内部 ID)、`doub_id`(豆瓣 ID)、`aurl`、`epic`(海报)、`title`、`ejs`(更新至X集/全集/空)、`niandai`(年代)、`ecc`(又名/类型/地区聚合)、`alias`、`class`、`production_area`、`seed_num`、`wp_num`、`imdbf` |
| `getVideoDetail?id=X` | 详情 49 字段（`id` 传豆瓣 ID；`release` 首播/上映日**仅老条目有值**） | 列表字段全量 + `otitle`(原题)、`episodes`(总集数)、`language`、`edit`(编剧)、`performer`、`abstract`、`long_time`、`is_show_seed`、`need_vip` |
| `getVideoTypeList` | 类型/地区/年代/画质/标签字典 | 筛选器元数据 |

> 筛选/排序参数（`sc/sd/se/sf/sh/sg/status` 等）、字典五维度全量取值、`release` 覆盖率抽样与播出日期可得性结论，均已实测并维护在 [butai0-api.md](butai0-api.md)。

### 关键字段语义（从页面渲染反推，需保守解析）

- `ejs`：`更新至9集` / `全集` / 空。剧集播出进度；电影通常为空
- `episodes`：总集数字符串，`"0"` 表示未知；`ejs=全集` 时代表已完结
- `seed_num` / `wp_num`：当前种子/网盘资源条数，站内热度信号
- `seed_updated_at`：资源最后更新时间，可判断"是否还在更新"
- `doub_id`：豆瓣 subject ID，可作为稳定外部身份用于后续对账
- `IMDB_number`：tt 开头的 IMDb 编号（详情/热门接口才有）
- 热门接口 `data.data` 双层嵌套；列表接口 `data.list` 单层——两种结构不同，解析必须分开写
- **分类不可信（2026-09-12 实测）**：列表接口行内无 `tp`/`type` 字段，分类必须以拉取来源 `sa` 参数为准；站点「电影页」会混入真剧集（如与萨曼莎·比第四季 `tp=1` 但 `ejs=更新至35集`），且详情接口的 `tp` 与站点归类矛盾——详情回写只补字段，不得覆盖库内分类
- **图床占位图（2026-09-12 实测）**：海报图床对失效 URL 返回 HTTP 200 的白底爆米花占位图（300x420、中心亮度 >0.85），客户端加载时必须拦截并回退应用内占位符，否则会永久缓存

### 反爬与限频

- 直接 `curl` 可访问，无 Cloudflare 拦截；1 秒间隔连发 5 次无限频
- 但适配器仍按全局规范 2 秒限频，保守使用
- 字段是私有接口，随时可能变化：解析必须容错（字段缺失不报错），URL 必须可配置

## 资源约束（2026-09-11 用户要求，硬性）

用户主力机是 8GB Mac mini，应用开机常驻，必须低内存、低磁盘：

- **磁盘**：SQLite 单文件，跟踪活跃作品 + 历史，一年也只几十 MB；海报磁盘缓存设上限（默认 300MB，可调低/关闭），LRU 淘汰，远小于 whatsnew 的 2GB+512MB。"关闭"语义（2026-09-20 明确）：不读不写磁盘，海报仅内存缓存；存量文件保留不清空，调回上限后由 LRU 逐步收敛
- **内存**：空闲内存目标 < 60MB（实测 15MB）；全原生 SwiftUI，不嵌 WebView；列表分页懒加载，不一次性载入全量数据；海报内存用 NSCache（系统压力下自动逐出）
- **CPU**：平时零定时器空转；同步是短促任务（默认低频如 6 小时一次，可手动触发、可关闭后台同步）
- **自启动**：暂未实现（普通窗口应用形态，二期可加 SMAppService 登录项）

## 同步与热度口径

### 同步范围（已定，2026-09-11 用户确认）

**活跃内容为主，不做全量拉取。** butai0 每天更新，全量 2.5 万条大多是老片，拉取无意义：

1. 热门榜三个（近日/本周/本月，各 35 条）——每次同步固定拉
2. 剧集/电影"按更新时间排序"的前若干页——覆盖在播、在更新的内容
3. 本地对比上一次快照，只对 `ejs` / `seed_num` / 评分变化的条目补拉 `getVideoDetail` 全量字段
4. 每个观察周期把 `ejs`、`seed_num`、评分写入本地历史表，形成"从 9 集更到 10 集"的进度时间线和热度趋势
5. 日常增量同步约 10~20 个请求（2 秒限频下一分钟内完成）；首次冷启动约几百个请求

### 榜单批次与变化展示（2026-09-14 实施，whatsnew 复用评估第 1-3 步）

- **批次写入是原子的**：每个榜单/每页列表一个事务，整批共享同一观察时间戳；任一条写失败整批回滚，旧榜不被半批数据替换。这解决 `latestChart`（按 scope 内 MAX(observed_at) 单秒切片）跨秒缺榜与中途失败两类正确性问题
- **写库失败计入同步摘要**（warning/failed），不再被 `try?` 静默吞掉
- **分榜单新鲜度**：每榜展示各自最后更新时间；本次同步某榜刷新失败时该榜显示"本次刷新未成功，显示上次数据"——全局成功不等于每张榜成功
- **名次变化标记**（热门榜卡片 NEW/↑n/↓n）：只比较同 scope 最近两个已提交批次；首次同步无基线不制造任何变化事件；"本次入榜"依据是上一批完整且不含该作品，不等于历史首次入榜；名次持平不标。不跨 scope 比较
- **碎片基线不作比较依据**（2026-09-14 补）：旧版本逐条时间戳的跨秒历史（生产库实测存在"27 条 + 3 条"式碎片）不满员时，会把缺观察误读成入榜——基线条数低于当前批次 85% 即不产生任何变化标记，宁可不标也不造假

### 同步状态展示（2026-09-15 定案）

- **顶栏三档**：failed 红色"同步出错"（一条数据都没拿到）；warning 琥珀"部分完成 · X 前"（主数据成功、部分步骤失败，如豆瓣 403）；success 灰色"已同步 X 前"。相对时间由前台 TimelineView 每分钟演进（无后台定时器，不违反零空转约束）
- **同步详情浮层**：点击顶栏状态弹出，内容来自 `SyncSummary.steps`（引擎逐步记录：三个榜单 / 电影剧集最近更新 / 条目详情补拉 / 首播日补全，各自 ok/partial/failed 与条数）+ 总量行 + 错误原文 + "下轮自动重试"说明。hover 保留简短 tooltip，点击看明细——信息层级两级
- 豆瓣 403 等 warning 场景的文案原则：明确"主数据已更新"，不让用户误读为整体失败
- 未做（评估文档保留项）：完整批次 ID 注册表、旧历史兼容、趋势图表

### 热度口径（一期，建议仅 butai0 单源）

- 热门榜（近日/本周/本月）+ `seed_num` 资源数 + 豆瓣/IMDb 评分
- 沿用 WhatsNew 教训：**保留来源、榜单范围与时间窗口，不做跨源混算排名**；`seed_num` 是站内信号，不是客观热度

## 列表筛选与首播时间线（2026-09-13 用户定案）

### 背景

用户反馈两个问题：① 应用无筛选而原站有；② 剧集页按资源更新时间排序，老剧（老友记第八/九/十季）重新供种即冒到第一页第 47-49 位。用户澄清后的核心诉求：**新剧老剧按整部剧首播日先后区分，剧集时间线按首播日倒序**；集数增加、重新供种、重新入库均不得改变排序位置。

数据可行性结论（实测档案见 [butai0-api.md](butai0-api.md)、[douban-premiere-date-assessment.md](douban-premiere-date-assessment.md)）：butai0 全接口无逐日播出数据（`release` 仅老条目有值，125 部播出中覆盖 0%）；tvMaze 中文剧覆盖≈0 不可用；豆瓣 rexxar 接口按 douban_id 可得 `pubdate` 首播日（国产在播样本 11/11 可得，无需登录）。

### 定案一：本地筛选（Q1-Q4，2026-09-12 批准）

- **纯本地筛选**：UI 对 SQLite 加 WHERE，不把筛选参数传给 butai0，不引入"浏览即请求"的第二套数据路径
- **范围**：只加在剧集/电影"最近更新"列表页；热门榜不加（榜单转述不应被二次筛选）
- **维度**：年代（复用原站字典 17 档）+ 状态（仅剧集页：播出中/已完结）+ 类型 + 地区。画质（本地覆盖率仅 14%）与标签（未存）不上
- **状态三态语义（2026-09-20 实施修正）**：站点 `ejs` 只有"更新至X集 / 全集 / 空"三态，故"播出中" = `episode_status LIKE '更新至%'`、"已完结" = `LIKE '全集%'`；空（未知状态）两边都不算，不冒充已完结。首版二值 `airingOnly` 的"已完结"分支与"全部"等价，属实现缺陷而非语义取消
- **注意**：`years` 有错标实例（重案六组标 2028，实际 2026-08-31 首播），年代筛选过滤的是"来源标注年代"，不承诺可靠的新老判断——可靠判断依赖定案三的豆瓣首播日
- **形态**：页头下菜单行（年代 ▾ 状态 ▾ 类型 ▾ 地区 ▾ | 清除）；筛选状态不跨启动持久化
- **默认排序**：Q6 定案后被首播日倒序取代（见下）

### 定案二：一期单源的明确例外——豆瓣仅补首播日（Q5，用户拍板）

**主数据仍只来自 butai0。豆瓣接入范围收窄为一件事：用库内已有 `douban_id` 请求 rexxar 详情，补 `pubdate` 首播日。**

- 端点 `m.douban.com/rexxar/api/v2/tv/<douban_id>`（剧集）/movie/（电影，本期不做），移动端 UA + Referer，无需 Cookie/Key
- **不得做**：标题搜索、评分/简介/海报/逐集补全、任何形式的身份匹配——只按已有 ID 直连
- 请求统一 ≥2 秒限频（与 butai0 客户端各自独立计数）；429 尊重 Retry-After，401/403/安全验证页停止当批并退避，不绕过
- **失败不阻断**主同步、不清空已有首播日；数据只存本地 SQLite（日期 + 来源 + 抓取时间），不上传
- **限频随机抖动（2026-09-14 红队审查定案）**：豆瓣限频从固定 2s 改为 6.5±1.5s 随机间隔——实测固定 2s 等差节奏两天累计 ~195 条后触发 403 风控，等差时间戳是教科书级爬虫特征；探针/熔断/凌晨集中等方案经红队审查全部缓议（403 是"请求中途触发的计数器"而非"时段开关"，三轮被拦分别在第 12/14/9 条，探针 200 ≠ 风控解除）
- **风控观测（只写不读）**：每次豆瓣请求无条件写 `douban_requests` 表（时点/条目/当轮第几条/HTTP 状态/结果分类），90 天与 observations 同口径裁剪。**熔断定案（2026-09-21 用户拍板）：不做熔断，仅保留观测**——6 天 558 条实测，403 全部集中在 9-15 当天 2 条（6.5±1.5s 抖动上线首日），9-16 起连续 5 天零 403，且 9-19/9-20 两天分别跑 177/265 条（含积压清偿放宽 60/轮）都零拦；此前"窗口计数器 12~14 条触线"假设被新数据削弱，6.5±1.5s 随机抖动已足够骗过节奏识别。后续建议：①代码侧零改动；②观测表继续运行，若 403 死灰复燃（用 `WHERE http_status=403 GROUP BY DATE(requested_at)` 一行 SQL 复测）再议熔断；③勿主动新增熔断/探针逻辑
- 取值规则（2026-09-13 用户定案"全都要"）：收集 pubdate 数组内**所有**完整 YYYY-MM-DD（不分地区），取最早一个 = 真实首播日；仅年份/无完整日期不补假日期（不把仅年份补成 1-1）；按自然日存，不做时区换算。原"仅中国大陆"白名单已废弃——豆瓣对日韩美剧有 "(韩国)" 等完整日期，白名单会让外剧永久无日期退回资源更新排序
- 无日期条目 24 小时后允许重查（豆瓣日期可能后来补上）；有日期的条目不重查

### 定案五：一期例外扩大到 TMDB——有 IMDb 的剧集补该季首播日（2026-09-15 用户拍板，方案 B）

豆瓣 403 风控退避期间，有 IMDb 号的欧美剧集（多为分季条目）补全停滞。**一期例外从豆瓣扩大到第二个外部源 TMDB**，范围收窄为一类条目：有 IMDb 号的剧集，补"该季首播日"（方案 B，不是系列首播日）。

- **口径：分季首播日**。用户剧集页是分季追踪（"黑袍纠察队 第四季""黄石 第五季"是独立条目），首播日取**该季** `air_date`，不是系列级 `first_air_date`——后者会把第五季错填成 2019 第一部年。实测本库 25 部有 IMDb 的剧集：TMDB 命中 24/25（唯一未命中的"与萨曼莎·比 S3"TMDB 无该 IMDb 条目，留空等豆瓣）
- **身份匹配：只按 IMDb 号直连 `/find?external_source=imdb_id`，不做标题搜索**（whatsnew 严格模式；豆瓣侧红线"不得标题搜索"同样适用于 TMDB）。关键实测：butai0 给剧集挂的 `IMDB_number` 多为"该季第 1 集"的单集条目（如权游 tt3658012=S5E1、最后生还者 tt26469967=S2E1），`/find` 命中 `tv_episode_results` 时其 `air_date` 即该季首播日，`episode_number==1` 一次调用直接采信；少数是系列级条目（夜魔侠重生 tt18923754 → `tv_results`），此时从库内中文标题解析季号（搬 userscript parseChineseNumber：第四季→4、第二十一季→21、Season N）再查 `/tv/{id}/season/{N}` 的该季 `air_date`；季号解析不出按第 1 季
- **季号校验**：库内标题解析得出的季号与 IMDb 单集返回的季号明显不符时（说明 butai0 挂错 IMDb），该条不硬填、留空等豆瓣
- **写库分源**：只在 `premiere_date` 为空时补，**永不覆盖豆瓣已有日期**（豆瓣是主源）；`premiere_source='tmdb'` 与豆瓣区分可反查回滚。无匹配/失败的条目留空（不置 `premiere_fetched_at`），留在豆瓣 24h 重查队列等退避。日期严格 10 位 YYYY-MM-DD，仅年份不补假日期（与豆瓣口径一致）
- **失败只计 warning 不阻断主同步**；401（key 无效）当批停止。**单周期 TMDB 请求沿用三档限速常量**（与豆瓣同一 PremiereBudget：稳态 10 / 积压 30 / 护栏 30）
- **限频**：TMDB 独立 RateLimiter ≥2 秒固定间隔（官方限流宽松，无需抖动），与豆瓣/butai0 各自计数
- **API Key 只存本地** settings.json（Application Support），不进 git、不上传、不打日志；未配 key 则跳过该步
- **不引入 OMDb**（CC BY-NC 非商业协议 + 仅镜像 IMDb 对国剧零增量，2026-09-15 审查排除）；52 部无 IMDb 的国漫/国产剧/日韩剧 TMDB 覆盖不如豆瓣，仍靠豆瓣退避后慢补，TMDB 不作标题搜索兜底

### 定案六：海报兜底——站方 localhost/http 事故条目从 TMDB/豆瓣补图（2026-09-18）

**背景（实测 2026-09-18，生产库）**：butai0 站方给部分条目（存量 70 条且新条目持续出现）挂的海报 URL 是 `http://localhost:3000/...`（站方发布事故，永不可达）；另有 124 条 `http://` 明文 URL 被 macOS ATS 静默拦截（图本身活着，App 内发不出请求）。用户确认设计不改（海报懒加载+缓存到底是对的），但要求"没图的自己去别处找图"。

- **兜底路由**：候选 = `poster_url` 为空 / 含 localhost / http 明文的条目。有 IMDb → TMDB `/find`（三种命中桶：movie_results/tv_results 直接带 poster_path；tv_episode_results 经 show_id 二跳 `/tv/{id}`）；其余有豆瓣 ID → 豆瓣 rexxar `pic.large`（`/tv/` 404 回退 `/movie/`——库内 kind 与豆瓣 kind 不一致实测存在，如"因果报应"）
- **写库口径**：直接写 `poster_url`（不加新列），只在现有值仍为坏 URL（空/localhost/http）时写；**upsert 同步防回滚**——站方再发 localhost 不覆盖已兜底的真 URL，站方修好给好 URL 则尊重站方
- **豆瓣图床防盗链**：doubanio 无 Referer 返回 HTTP 418（实测），PosterLoader 对 `*doubanio.com` 域名补 Referer + 桌面 UA
- **限频护栏**：豆瓣路径沿用 6.5±1.5s 抖动 + 每轮 ≤30 条（PosterBudget）+ douban_requests 观测表（outcome=poster_got/poster_404）；TMDB 一轮扫完（官方限流宽松）。失败只计 warning 不阻断主同步
- **不做**：标题搜索建身份（错配红线不变）、不覆盖站方好 URL、不为 mvinfo.homes 加 ATS 全局明文例外
- **S3 海报镜像（2026-09-18 用户定案，同日实施）**：站方图床整体迁移到 `img.mvinfo.homes` 且只配 http（443 无证书，TLS 握手失败；旧 tu.mvinfo 的 https 还活着但站方已改写全部条目 URL，不可达）——**http 将是常态**，海报获取改为"App 侧搬运"：兜底取到的外源图（TMDB w500 / 豆瓣 pic.large，均 https）先镜像到用户自有 S3 兼容桶（RustFS/MinIO，NAS 哑存储，不跑任何服务），`poster_url` 写桶 URL。用户 NAS（极空间）无法跑抓取脚本，故镜像由 App 完成——App 只拉 https 外源图再 PUT 进桶，不触碰站方 http 图床
  - **ATS 合规**：桶端点为局域网 http（如 `http://192.168.1.10:9000`）时由 Info.plist `NSAllowsLocalNetworking` 豁免——Apple 官方 ATS 例外，仅放行本地网络（RFC1918 私有 IP / .local），**不为任何第三方域开明文例外**；站方 http 图床继续一律不请求
  - **S3Client**：SigV4 签名（CryptoKit HMAC-SHA256，零第三方依赖；签名原语已与 Python 独立实现对拍一致），path-style 寻址；mirror = HEAD 探测已存在则跳过 → PUT 上传；401/403 当批停止，桶暂不可达（NAS 关机）降级直写外源 URL 不阻断
  - **配置**：settings.json 四项（endpoint/bucket/accessKey/secretKey，只存本地不进 git），设置页"S3 海报镜像"卡片；任一为空 = 关闭镜像，兜底直写外源 URL（豆瓣图需 Referer，PosterLoader 已按域名处理）
  - **实施状态（2026-09-19 实桶对接完成）**：RustFS（用户 NAS 局域网端点）建桶 `whatshot-posters` + 匿名只读策略（仅 `s3:GetObject`）；全链路实测通过（建桶幂等 → 豆瓣图下载 → 镜像 → 匿名读回字节一致）。S3Client 首版三处实测 bug 已修：① dateStamp 派生 `dropLast(7)` 漏掉日期后的 'T'（应为 dropLast(8)，RustFS 报 invalid header）；② exists() 只看"未抛异常"，HEAD 404 被误判已存在跳过 PUT（改为显式查 `statusCode == 200`）；③ SigV4 canonical headers 块与 signed headers 之间必须有一个空行（与 botocore 对拍定位）。端点/凭据同时存项目根 `.env`（已 gitignore）与用户本机 settings.json
  - **清偿节奏（2026-09-19）**：存量事故条目约 520 条（localhost 70 + 站方改写 http 523 的一部分），豆瓣路径稳态 30 条/轮、积压 >100 条时放宽 60 条/轮（9-19 实测两轮 30 条全 200 无 403）；手动同步无冷却可连跑加速
  - **镜像候选语义（2026-09-20 修复）**：桶 URL 虽是 http 明文但是可信自有存储，`posterBackfillCandidates` 按桶前缀 `{endpoint}/{bucket}/` 排除——否则已镜像条目每轮重复进队列，反复外源下载+探桶并挤占兜底预算。配 S3 时 https 外源 URL 纳入待镜像：镜像降级直写外源的条目由此获得下轮重试入口（桶恢复后自动补镜像），配 S3 前直写的镜像存量也一并清偿；`setPosterBackfill` 仅在 `allowHttpsOverwrite`（= S3 已配置）时允许改写 https 现值，未配 S3 保持"站方好 URL 不覆盖"原口径。撤销 S3 后旧桶 URL 回到坏图队列重新补图，行为自愈

### 定案七：本地搜索、追剧、更新汇总、同步阶段与停止（2026-09-20 用户授权实施）

- **本地搜索**：列表页搜索框（⌘F 聚焦，250ms 防抖），片名/原名/别名本地 LIKE（通配符转义按字面匹配）。**只搜已同步内容，不触发外部标题搜索**；与筛选、排序组合，分页共用
- **我的追剧**：`watchlist` 表（video_id + created_at），详情浮层关注/取消，新增"追剧"标签页（海报行 + 最新集数 + 已完结标注 + 检查时间）。**同步范围扩展的边界（对"只做活跃内容"的显式例外）**：每轮同步对追剧条目做 detail 单条刷新，上限 20 条、最久未检查优先（2 秒限频下约 40 秒）——离开热门榜与最近更新页的作品靠它保持更新，否则追剧只是书签；关注较多时自动分轮，多数追剧作品仍在活跃范围被常规同步覆盖
- **更新汇总**：追剧页顶部"自上次查看 · N 部有更新"区块 + tab 未读圆点。口径：水位 = max(上次查看时刻, 关注时刻)，比较水位前最近一条与水位后最新一条的 ejs——关注前历史不报（首次不制造伪更新）、首尾比较不因重复同步重复报、集数回退如实展示方向、无基线不报；时间为本地发现时间，不冒充播出日。水位存 UserDefaults（只存本机）
- **同步阶段与停止**：顶栏实时显示当前阶段与补全计数（引擎 `onProgress` 回调）；同步中可点"停止"——cancel 引擎 Task，各补全循环在步骤边界退出，**已提交批次保留、事务不中断、不冒充成功**：sync_runs 记 `stopped`（计入 lastSuccessfulSync，主数据已保留），顶栏显示"已停止"，详情浮层注明未执行补全下轮自动继续

### 定案八：可选外部热度——用户自有 WhatsNew 服务接入（2026-09-22）

**背景**：用户认为 butai0 榜单不够准确。方向：先用追剧保留喜欢的作品（定案七不动），再引入用户自有 WhatsNew 服务（NAS/局域网，参考站 ../whatsnew 只读）的其他来源热度作为发现作品的补充。**不是多源热度叠加混算**——外部信号单列展示，但ai0 排名/评分/集数口径全保留，原热门榜与默认排序不变。

- **可选接入**：settings.json 新增 `whatsnewBaseURL`/`whatsnewEnabled`（显式 true 才发请求）；关闭或未配置时同步整步跳过**零请求**，离线不影响追剧与原同步
- **只读三端点**（WhatsNew API 实测，2026-09-22 对码核对）：`/api/health`（验证 `service == "whatsnew-backend"`，HTML/错误服务不算成功）、`/api/trending`（无筛选=工作中心，按 heatScore 选最多 50 部活跃作品返回全部当前信号；带信号级筛选改 50 条截断——**未出现只能解释为"本次范围未覆盖"**，不能推断下榜）、`/api/media/:id`（补豆瓣身份用，≤10 条/轮）。**无批量身份查询端点**，如需给任意追剧作品准确补信号需 WhatsNew 端新增接口（建议有限批量按 IMDb/豆瓣 ID 查询，未实现——跨仓库写入需另行授权）
- **匹配（保守）**：只做稳定 ID 精确相等——IMDb 号（规范化小写）与本地 `imdb_number` 相等、或 WhatsNew `MediaSourceRef` 的 `douban-<数字>` 与本地 `douban_id` 相等；电影/剧集绝不互配；双 ID 分别命中不同本地条目 = 冲突不匹配不擅自选；**不做标题相似度、不做系列→季推断**（WhatShot 库内 imdb_number 常为"该季第 1 集"单集 tt 号，WhatsNew 是作品级，精确相等漏配的条目如实显示"未关联"）。同榜多季靠 `rankingEntryKey` 天然多席位，不按作品去重
- **展示**：独立"外部热度"标签页按 source 分组，行显示名次、标题（匹配→本地条目可点进详情；未匹配→WhatsNew 标题）、来源/平台/地区/季标签、站方采集时间（`capturedAt` ISO 原样保留）；**保留来源、榜、窗口与季版本，不伪装统一总榜**。详情浮层对匹配作品显示"外部热度 · WhatsNew"区块。本页零网络请求（读本地快照）
- **持久化**：`external_heat` 快照表，UNIQUE(media_id, source, ranking_scope, window, ranking_entry_key) upsert 覆盖——**不因本次响应未返回而删除/翻转旧行**（trending 50 条截断下"未返回"≠下榜），行数由 UNIQUE 封顶；`external_heat_state` 单行连接状态（never/ok/unreachable/bad_service/invalid_response），失败保留上次成功时间与已有缓存
- **同步步骤**（SyncEngine 可选步骤，whatsnew 客户端注入才有；独立 2 秒限频，与 butai0/豆瓣/TMDB 各自计数）：health → trending → 本地身份点查（`imdb_number IN (...)` / `douban_id IN (...)`，不全量载入）→ IMDb 直连匹配 → 未匹配条目按 mediaId 去重后 ≤10 条 detail 补豆瓣 refs → 二次匹配 → 事务写库（一次成功响应一个事务，整批同 fetched_at，失败整批回滚）。任何失败只计 warning，不阻断主同步与追剧
- **隐私**：WhatsNew 地址只存本地 settings.json，不进 git、不上传、不打日志；现有 trending 拉取不发送追剧清单；detail 补查只带 WhatsNew 内部 ID（不带任何本地数据）。WhatsNew 服务仅限可信内网，App 不为其做公网暴露
- **新鲜度口径**：显示"站方采集 capturedAt（ISO 原文）+ 本地发现 fetchedAt（相对时间）"两个时间；客户端成功取到响应的时间不冒充榜单更新时间。自动失效策略（按来源窗口过期）初版不做，展示原文由用户判断

**验证状态（2026-09-22）**：单元测试 17 项（解码/匹配/持久化）+ 引擎集成测试 4 项（URLProtocol stub 模拟服务：成功链路/服务不对/不可达保缓存/畸形响应）全绿，全量 102 项通过；`dist/WhatShot.app` 本机打包成功。**真实 WhatsNew 服务联调未验证**（本机无运行中的 whatsnew-backend，19993/19992 均未监听；用户 NAS 实际地址与部署版本未提供）——模拟测试不能替代真实联调，覆盖统计与未匹配比例待用户配置真实地址后首轮同步核对。

### 定案四：补全节奏（Q9，2026-09-13 实测定稿）

- **首次接入**：一次性全量补剧集库（当前 265 部，全部有 douban_id；2 秒间隔串行约 9 分钟，后台执行）
- **之后**：挂进现有同步周期（默认 6 小时，可调 4 小时），三档限速：
  - **稳态**：每周期最多 10 条——实测依据：本地 7 轮同步记录稳态每轮新增 0-6 部；且按 10 页×25 条实测拉取，250 条中 249 条已在库——**新增量由站点更新速度决定，与列表页数设置基本无关**，10 条覆盖稳态有余量

- 首播日不随集数更新重抓；`pubdate` 修正（豆瓣改档期）时以新抓取为准覆盖
- 三档阈值为代码内可调常量（工程韧性参数），不进用户设置页

### 定案十：WhatsNew 批量身份查询接入（2026-09-23）

WhatsNew 端已交付只读批量身份查询端点（`POST /api/media/lookup`，契约 v1， WhatsNew commit `5806050`/`a24999a`），WhatShot 端对接：

- **追剧反查**：每轮同步对追剧条目（≤20 条、按 movie/series 分批、每轮各 ≤1 次请求、2 秒限频）反查 WhatsNew——**不在 trending 50 部内的追剧作品也拿得到信号与评分**；matched 的信号写 `external_heat`（video_id 直填、外部热度页与详情展示"已关联"）、评分写 `external_media_details`（详情浮层评分对照自动生效）。unmatched（含单集 tt 号—— WhatsNew 不做单集桥接，WhatShot 库内剧集 tt 号多为该季第 1 集的单集号）如实跳过，不是 bug。
- **三种"没有"分开**：unmatched（库内无此身份）/ matched + signals 空（在库但无当前信号）/ 4xx 请求级错误——消费方据此区分"没收录/下榜/查询坏了"。
- **base URL 只走 settings.whatsnewBaseURL 可配置项**（连调用的测试实例地址不硬编码进任何代码，正式部署后用户回传新地址改设置即生效）。
