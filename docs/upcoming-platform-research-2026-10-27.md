# 四平台待播时间线调研（2026-10-27）

> 2026-10-28 更新：腾讯新增电影首页「VIP即将上映」排期证据，原“只做待定档”结论已修正；芒果不接入。详见文末入口纠正与最新设计。

状态：调研建议，尚未定案或实现。用户要求先查 WhatsNew、PixelReel 的既有经验，再判断 WhatShot 新增「即将上线」标签页的数据源。

## 结论

优先做优酷电影，爱奇艺作为日期级补充；腾讯暂用于待定档候选，芒果暂缓。判断依据是日期与时刻的实际覆盖、已有实现和本次复测，不是「反爬最弱」的假设。

能够准确展示平台已经公布的日期与时分，不能保证每部作品都有时间。现有入口也不能提供四平台所有作品的完整排期。优酷剧集节点本次没有任何明确日期，不能把电影样本的能力推广到剧集。

## 本次真实复核

通过 kimi-webbridge 访问真实浏览器页面；另外按 WhatsNew 的公开读取协议，用独立临时探针验证无需浏览器登录态的优酷请求。没有读取用户 Cookie，没有启动 WhatsNew 后端或执行同步 CLI，没有写入任何业务数据库。

### 优酷

页面：[电影频道](https://www.youku.com/ku/webmovie)。

- 浏览器确认「新片·即将上线」模块，首屏内嵌组件有 19 条卡片和「查看全部」。不能把这 19 条当作全部待播。
- 页面内嵌内容是 JavaScript 对象，直接作为严格 JSON 解码会在 `undefined` 处失败；不建议为此执行整段远端脚本。
- 按已有适配器协议复测 `mtop.youku.columbus.gateway.new.execute`，使用 `kuflix_node_page / PIANDAN_HEATLIST`。
- 电影节点 `22861692`：4 页，最终 `more=false`，79 个不同 show ID；其中 4 条日期文本明确到时分，74 条为「敬请期待」，另 1 条标签为「影」。
- 剧集节点 `22916606`：8 页，最终 `more=false`，144 个不同 show ID，本次全部「敬请期待」。
- 这里的「完整」只指当前节点分页读取完毕，不意味着平台全片库覆盖。
- 匿名令牌在内存中使用；同一服务请求由 RateLimiter 保持至少 2 秒间隔。本次成功证明当前可读，不证明长期不会风控。

本次公布的时间，统一按北京时间解释；「明天」以 2026-10-27 的页面观察日期转换：

| 作品 | 来源原文 | 展示日期与时刻 |
|---|---|---|
| 燃烧吧！爸爸 | 明天16:00上线 | 2026-10-28 16:00 |
| 挺好的 | 明天16:00上线 | 2026-10-28 16:00 |
| 玩具总动员5 | 10月30日 10:00上线 | 2026-10-30 10:00 |
| 偷天陷阱 | 10月31日 10:00上线 | 2026-10-31 10:00 |

额外发现：`杯雪·一战成名` 卡片没有 `reserve`、有 `trackShow`，旧解析的兜底文本取到了「影」。不能仅因条目位于该节点就认定它是待播预约，迁移时须校验预约或明确待播证据。

海报原始地址有 HTTP。抽检 `liangcang-material.alicdn.com` 和 `m.ykimg.com` 各一个对应 HTTPS 地址，HEAD 均返回 200、`image/jpeg`；仅说明这两个样本支持 HTTPS，不能无条件放宽 ATS 或声称所有海报可用。

### 爱奇艺

页面：[独立待播页](https://www.iqiyi.com/newOnlinePCW)。

- 当前 `window.__NUXT__.data[0].allVideos` 有 378 条；9 条 `publishText` 含月日，0 条包含时分。
- 例如「玩具总动员5」为「10月30日上线」，没有 10:00；不能借优酷的 10:00 填给爱奇艺。
- 本次字段包含平台 ID、标题、分类、海报、`publishText`、`isOnline`、预约人数，没有在这些记录中发现精确上线时刻字段。
- 这表示该入口目前提供日期级信息，不代表爱奇艺所有其他入口都没有时刻。
- WhatsNew 已有 HTTP 页面读取实现；PixelReel 早期「必须 Playwright」的判断不应继续照搬。迁到 Swift 仍需解决 Nuxt 数据安全解析，不能照搬动态执行远端脚本的方式。

## WhatShot 的建议形态

新增「即将上线」标签页，以日期分组、组内按北京时间排序；先接优酷电影。已公布日期但没有时分的作品显示「时间待公布」；没有日期的放「待定档」，不能填成 00:00。爱奇艺可在后续补充日期级片单。

记录至少保留平台、平台作品 ID、片名、海报、来源链接、日期、可空的时分、原始日期文案及采集时间。平台上线时间应独立于 WhatShot 现有的作品首播日，不写回现有首播日字段，不把预约数加入 butai0 热度榜。同名作品不直接合并；跨平台每个平台保留自己的排期。

遵守现有纯本地架构时，可将 WhatsNew 已验证的优酷 HTTP 协议迁成 Swift，使用现有 SQLite、海报缓存与限频机制，浏览器只用于调研。新增标签页和本地存储属于后续实现，本轮不修改需求定案。

如果以后明确接受依赖 WhatsNew 服务，也可研究读取其排期 API；但当前 `/api/calendar` 会过滤无日期条目、截断返回结果，不能直接声称覆盖本需求的待定档和完整时间线。该路线需要另行约定接口和部署依赖。

## 红队自审

### 🔴 致命弱点（必须解决，否则整体失效）

1. **把「精确到几点」承诺给全部作品。** 优酷电影仅 4 条明确时分，剧集 144 条均无日期。任何默认时刻、跨平台复制时刻都会制造假精度。必须按来源实际精度展示。
2. **把待播时间当作已可看证明。** 页面公布的是计划，可能改期；预告也可以播放。到点只能显示「按排期应上线／待确认」，不能仅凭系统时钟标成已验证上线，更不能保证会员、付费或地区可看条件。

### 🟡 主要缺陷（应该解决，影响质量和可信度）

| 缺陷 | 严重程度 | 处理边界 |
|---|---|---|
| 一次成功推断反爬弱 | 高 | 本次只证明当前匿名读取成功；接口失效保留上次成功快照并显示过期 |
| 旧代码遇到已过去的月日一律加一年 | 高 | 昨天的残留条目会被误排到明年；需要基于来源观察时间、跨年窗口及历史记录消歧，无法确定时保持原文 |
| 节点混入无预约的卡片 | 高 | 本次有真实反例；按预约或明确待播证据筛选，不靠栏目位置推定 |
| 半批分页失败误判下架 | 高 | 成功完整分页后才替换来源快照；超时、缺字段、达到上限都不能覆盖为完整空列表 |
| 日期受机器时区与页面缓存影响 | 中 | 显式使用 Asia/Shanghai，保留原文和采集时间，尽量核对响应或页面生成时间 |
| 轮询间隔与排期精度混淆 | 中 | 6 小时同步也能存 10:00，但不能保证提前发现临时改期；界面明确最近核实时间 |
| 海报 HTTP 与 ATS 冲突 | 中 | 仅使用验证可用的 HTTPS，同源失败显示缺图，不增加公网 HTTP 豁免 |

### 🟢 改进建议

1. 用今天这 4 条日期、无日期、无预约、跨年残留、改期、分页失败作为迁移验收样本。
2. 优酷电影先完成「匿名读取 → 完整分页 → 日期精度 → 本地快照 → 时间线」闭环，再增加平台。
3. 爱奇艺保留日期级能力；腾讯保留待定档能力；芒果找到可核验排期入口后再定接入。

### 📋 审查总结

- 整体评估：优酷适合首先落地已公布排期的电影时间线；四平台全部作品精确到时分的目标，目前证据不支持。
- 最高优先级行动：落实日期精度和待播身份校验，不能直接复制旧适配器的全部判断。
- 如果不改：会产生虚构时刻、错误跨年日期和非待播作品混入，时间线看起来完整但不可信。

## 2026-10-28 入口纠正

用户提供电影首页「VIP即将上映」后，已通过 Kimi 真实页面与独立匿名请求找到 `film.video.qq.com/x/autovue/film_index/cgi/getModList` 的 `type_58` 栏目。`cms_data.show_date` 给出平台排期，三条截图样本为《兰香如故·花胜秋宴》2026-10-29 12:00、《玩具总动员5》2026-10-30 10:00、《宝莲灯凡心问天》2026-10-31 10:00。后续匿名读取又出现《敦煌英雄》10 月 29 日 10:00、《痴迷》10 月 30 日 10:00，说明页面快照会随编辑排期更新。

上文“腾讯只做待定档”是旧片库入口的调查结论，已由此次新证据修正；仍不使用 `publish_date`。WhatShot 保留原片库并新增 VIP 排期，具体实现、分类范围及失败边界见 [设计补充](plans/upcoming-timeline.md#腾讯-vip-排期修正2026-10-28)。芒果已按用户决定不接入，历史调研记录不代表当前接入计划。


同日稍后再核验：匿名接口与重新打开的真实网页均改为仅《兰香如故·花胜秋宴》《痴迷》两条明确排期，其余上述电影移出了该次 VIP 栏目列表。应用已跟随当前来源，不保留已失去该栏目依据的旧时间；这也进一步限定了“稳定”的含义：匿名技术链路可用，不代表栏目成员或排期数量恒定。
