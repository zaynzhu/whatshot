# 电影上映日期：本地解析优先的执行路线

日期：2026-10-15。适用基线：`07da1d7`（电影页已新增新片优先）。
状态：研究与只读验证完成，尚未实现正式功能；未改真实数据库、同步逻辑或 App 产物。

## 目标与已确认口径

让电影的新旧顺序比影片年份更准确，保持既有功能稳定，不为日期扩大成多源抓取工程。

用户已确认：电影优先采用正式公映或网络上线日期，尽量排除电影节首映。这与剧集“所有完整日期取最早”的既有规则不同，必须保留独立解析入口，不能直接修改共享剧集解析器。

本路线建议（不是新的用户定案）：

- 从已保存的站方 `release_info` 解析日期；先完成零新增请求的阶段。
- 在未明确限制地区的前提下，取各地区符合口径的最早日期，不默认中国大陆优先。
- 明确的电影节、影展、电影展、电影周、首映活动、点映、重映不作为正式上映日期；只有这类日期时保持未知。
- 有地区或上线渠道标签、且没有上述特殊场次标注的日期作为站方上映日期候选。来源仍标 butai0，不能因为站方可能转载豆瓣就标成豆瓣直取。
- 只有无标签日期的条目，首阶段暂不写标准上映日期；保留原文供查看。标签不完整、错误或未来出现未识别的场次，都可能使判断失效，不宣称独立核实了公映事实。
- 不把年份或年月补成 1 月 1 日，不把首次入库、资源更新当上映日期。

## 当前证据与原型

此前“724 部电影没有上映日期”的说法不完整：`premiere_date` 确实全空，但 `release_info` 已经含有大量原始日期。

全库只读统计（2026-10-15）：

| 项目 | 数量 | 能证明什么 |
|---|---:|---|
| 已同步电影 | 724 | 当前本地范围，不是站方全库 |
| 标准日期非空 | 0 | 电影尚未接入日期归一化 |
| 原始上映信息去空白后非空 | 501 | SQL 单纯判断不等于空串会得 502，其中一条仅空白 |
| 含合法完整日期（不排除特殊场次） | 491 | 仅证明日期可解析，不等于符合公映口径 |
| 排除特殊场次且有标签的候选 | 441 | 可进入首阶段本地解析，约占 61% |
| 只有无标签日期 | 42 | 类型待核对，不自动当公映 |
| 无可用日期／仅特殊场次／仅年月年份 | 241 | 首阶段保留年份显示 |
| 2025—2026 年电影 | 272 | 当前年份及上一年 |
| 上述近期电影有带标签候选 | 234 | 约 86%，是本地优先的主要收益 |
| 候选日期年份与影片年份不同 | 29 | 不能一直用原始年份作为日期排序的第一关键字 |
| 候选日期晚于观察日 | 0 | 当前未出现，不代表未来不会出现，仍需边界测试 |

其他来源约束：724 部都有豆瓣 ID，337 部有 IMDb ID；只有 11 部电影已关联本地 WhatsNew 外部热度缓存并有 `first_release_date`。这些数字不能推导为外部服务的总覆盖率。WhatsNew 日期借道仍属既有暂缓项，不在本路线自动启用。

实例：

- 《大器晚成》：`2025-08-29(威尼斯电影节), 2026-08-07(美国)` → 候选 `2026-08-07`，不选电影节日期。
- 《今晚正好》：`2026-05-22(中国大陆), 2026-04-19(北京国际电影节)` → 候选 `2026-05-22`。
- 《调音师》：两条日期均为电影节 → 保持正式上映日期未知。
- `2026(未定)`、`2025-06(电影节)` → 不造完整日期。

只读原型：[`experiments/movie_release_probe.py`](experiments/movie_release_probe.py)。使用 Python 标准库，不联网，以 SQLite `mode=ro` 打开库，不输出凭据或设置。它只验证候选解析与覆盖率，不能作为正式 Swift 实现直接交付。

复现：

```sh
python3 docs/plans/experiments/movie_release_probe.py "$HOME/Library/Application Support/WhatShot/whatshot.sqlite3" --as-of 2026-10-15
```

实际结果：12 个解析边界断言通过；上述统计来自全量本地电影记录。覆盖多地区逗号、中英文括号、特殊场次、仅年月、非法日期与闰日。未调用豆瓣或 TMDB，不证明外部接口当前可用或其返回能提升多少覆盖率。

相关代码用途：

- `macos/Sources/WhatShotCore/Models/ButaiModels.swift`：`release` 已由主源详情解码。
- `macos/Sources/WhatShotCore/Persistence/VideoRepository.swift`：保存 `release_info`，已有 `premiere_date/source` 字段与分页排序；当前日期候选限定剧集。
- `macos/Sources/WhatShotCore/Networking/DoubanClient.swift`：已有 `/movie/` 海报请求通道；但日期接口硬编码 `/tv/`，且现有解析器会保留电影节日期，不能直接复用其语义。
- `macos/Sources/WhatShotCore/Networking/TmdbClient.swift`：现有日期专为剧集分季设计，电影海报命中不等于电影上映日期契约已经实现。
- `docs/butai0-api.md`：2026-09-12 的低覆盖结论主要来自剧集样本，不能直接套用到当前电影数据。

## 对抗性自审

### 致命弱点

若直接复用剧集“取最早”解析，105 部含电影节标注的电影会面临错误口径，用户刚确认的要求无法成立。电影必须独立过滤场次，并用真实日历验证日期；现有解析器主要校验字符串形状，不足以拒绝 2 月 30 日。

### 主要缺陷

- 没标电影节不等于已独立确认公映：首阶段只承诺站方候选，保留原始文字和来源，未注明类型的 42 部暂不采信。
- 已知日期一律排在未知之前，会把年份为 2026、缺月日的新片压到 1998 年老片后面；必须保留年级别回退。
- 排除电影节后可能跨年：29 部现有记录已出现该现象，不能继续用原始影片年份压过有效公映年份。
- 立刻全量补查 283 部会增加外部请求和风控压力；海报已补齐的条目也不一定再触发海报请求，不能把“顺带拿日期”当成全部补齐的保障。

### 改进建议

先用本地字段覆盖近期电影的大部分需求；未知日期保持可解释的年份排序。缺口补查单列后续阶段，不与本地解析捆绑上线。

### 审查总结

当前证据足以支持小范围本地实现，不足以承诺全库公映日期正确或全量可补齐。最高优先级是电影独立的场次过滤和混合精度排序测试；不处理这些，可能有日期反而比只有年份更误导。

## 首个可执行阶段：仅本地归一化

前置条件：用户明确要求实施此阶段。当前请求为研究“怎么办”，本轮不自动迁移真实数据。

1. 先复跑只读原型，核对当前覆盖率与异常标签；读 `AGENTS.md`、`CLAUDE.md`、本路线及需求文件。正式改动前把电影口径写入 `docs/requirements.md`，区分已有剧集口径。
2. 实现电影独立解析器：输入原始上映字符串，输出可选 YYYY-MM-DD；严格公历日期、排除特殊场次、多个合格日期取最早，缺少类型标签则返回空。用上述实例与测试边界固定行为。
3. 复用现有标准日期字段，限定 `kind = movie`、仅从 `release_info` 推导，来源标 `butai0`。存量本地记录在一个事务中处理，分批读以避免载入全量海报；按条目主键更新，不能用可能重复的豆瓣 ID 跨条目写入。回滚与重复执行必须安全；本轮未执行此步骤。
4. 新增／更新主源详情时同步归一化。只允许重算本路线自己派生的 `butai0` 日期，其他来源日期不得被覆盖；列表响应缺失 `release` 时保留库内原文与日期，不能误清空。日期原文真的修正时重新解析，防止只补空导致已知错误永不更新。
5. 沿用“新片优先／资源更新”两个入口。新片优先：有效非未来日期取其年份，否则回退合法影片年份；年份倒序，同年内完整日期倒序、无月日排在同年末尾，最后按资源更新时间与 ID 稳定排序。未来完整日期、未来年份和异常年份排尾；不造虚假的日期来完成排序。明确的有效日期优先于相冲突的原始年份。
6. 电影卡片有日期显示“上映 YYYY-MM-DD”，无日期仍显示影片年份。保留来源与原始上映信息可查；原有资源更新、剧集首播排序、海报、S3 和同步请求范围不变。

验收：

- 多地区括号内逗号不误拆；电影节先于公映选公映，只有电影节保持未知；仅年份／年月／无标签／非法日历日期不误填。
- 原始年份 2025、公映日期 2026 的电影按 2026 排；2026 年未知月日不被 1998 年完整日期挤到后面；同年完整日期与未知日期排序确定。
- 将观察日固定后覆盖同年未来日期、闰年、缺失年份，分页不重复不漏项，搜索与筛选绑定正常。
- 事务失败整批回滚，重复执行不改已正确结果；列表空字段不清日期，详情纠正可重算，外源日期不覆盖。
- 主源／豆瓣／TMDB 请求数不因这一步增加；不触发上游全库抓取。
- `scripts/test-macos.sh --filter 'VideoRepositoryTests|PremiereTests'` 加新增电影解析与集成测试通过，随后本机打包、检查显示并按原子任务提交。这里列的是后续验收命令，本轮未执行正式功能测试。

## 后续方向与未知边界

本地实现使用一段时间后，如果未知日期确实影响选片，再推进缺口补查；不是本路线自动授权的附带工作。

- 优先评估现有豆瓣 `/movie/<douban_id>` 的 `pubdate`，身份直连、禁止标题搜索、沿用电影场次过滤。先挑少量“无原文／仅电影节／无标签”样本验证实际收益，未验证前不能承诺补齐。
- 建议首轮最多 5 条，从既有同服务预算划分而非另开独立限频器或抬高总请求量；继续使用项目已有间隔、退避及失败保护。共享预算对剧集补全的影响需要验证，不能让电影积压挤占剧集更新。
- 若已有海报请求正好返回这些字段，可在同次响应中取日期；不能为了顺带补日期重新触发已完成的海报任务。
- TMDB、WhatsNew 暂不新增为日期回退。后续若使用，必须先核实日期是否满足正式公映／网络上线语义，不能直接拿一个未区分场次的 `release_date/firstReleaseDate` 混用。
- 未来日期当前样本没有覆盖；接口可用性、缺口真实可补率、站方日期真实性均未通过联网验证。进入这些未知区域时，由用户选择继续验证或维持本地方案。

必须交回判断的变化：改为中国大陆优先；接受无类型标签或电影节日期作正式上映日；跨源覆盖已有日期；增加抓取总预算；需要改 WhatsNew、引入后台服务或新存储结构。不得为提高覆盖率悄悄放宽规则。
