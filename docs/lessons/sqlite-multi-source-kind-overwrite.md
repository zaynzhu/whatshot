# SQLite 多来源 upsert 的字段覆盖语义

结论速览：
- **方案**：多个来源各自携带分类/枚举值 upsert 同一行时，UPDATE 用"只升不降"的 CASE 守住已有值：`kind=CASE WHEN videos.kind = 2 THEN 2 ELSE excluded.kind END`——同一条目被电影页（kind=1）与剧集页（kind=2）先后拉取，互相覆盖会让条目在两个 tab 间闪烁。
- **适用**：本机 WhatShot（SQLite 系统 C 库）；任何"同一行被多个来源以不同枚举值 upsert"的持久层设计。

## ✅ 多来源 upsert 互相覆盖枚举字段 → 条目在两个分类视图间闪烁（2026-09-23）

- **为何值得记**：用户报告"电影 tab 剧集混进去"（截图实证），查库时 kind 却是正确的——时序差掩盖根因；从"站点电影页混入真剧集"的既有定案（2026-09-12）+ 同步阶段时序推演才闭环，共 2 轮定位。
- **最终方案**（VideoRepository.writeEntry）：
  ```sql
  ON CONFLICT(id) DO UPDATE SET
    kind=CASE WHEN videos.kind = 2 THEN 2 ELSE excluded.kind END,
    ...
  ```
  语义：kind=2（剧集）一经写入恒保留；kind=1（电影）被剧集类来源拉到时升级为 2。**INSERT 的 kind 列本身仍用来源值**（首次入库语义不变）。
- **为什么这样做**：站点"电影最近更新页"混入真剧集（2026-09-12 既有实测），同步顺序是电影页→剧集页，互相覆盖：
  - 恒保留（第一版修复）：消除闪烁，但"首次被电影页错标为电影"的剧集会固化——权衡反转
  - 只升不降：kind=2 恒保留（不闪回）、错标剧集被剧集页拉到时自愈升级、详情 tp 把剧集标成电影的旧隐患（preserveKind 旧语义）一并封死
- **适用条件**：枚举值有明确的"权威方向"（此处：剧集特征不可逆）；若枚举值双向合法，此规则不适用，需另设来源权威表。
- **验证证据**：110 项测试全绿（含新增 `upsertKeepsExistingKind`：kind=2 保留 ✓、新条目用来源 kind ✓、kind=1 被剧集页拉到升级 2 ✓）；生产库证据——用户截图时电影 tab 显示 kind=2 条目、几分钟后查库同条目 kind=2 正确（同步进行到不同阶段的数据时点差）。
- **易错点**：
  - 查库时点与用户报告时点不同步，库"看起来是对的"不等于 bug 不存在——**同步进行中的中间态**才是用户看到的。
  - 修复"互相覆盖"时，"恒保留"会引入新的固化错误（首次错标固化）——枚举有方向性时用"只升不降"，不要一刀切。
- **交叉验证**：两轮定位（库证据→UI 排序反推→解析层定案）+ 110 项测试含新用例；单 agent 结论，无多 agent 审查。
