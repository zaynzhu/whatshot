# 客户端先行、服务端部署滞后的过渡降级

结论速览：
- **方案**：客户端先行接入新端点、服务端（用户自部署服务）尚未部署新版时，端点 404 视为"版本未部署"**静默降级**（不产 warning、不阻断主流程，部署后自动生效）；网络失败等其他错误照常如实报警。
- **适用**：本机 WhatShot（用户自有 WhatsNew NAS 服务，部署节奏由用户掌控）；任何"消费端先发、服务端部署滞后"的过渡期。

## ✅ 新端点在旧版服务上 404 → 静默降级而非反复 warning（2026-09-23）

- **为何值得记**： WhatsNew 端交付了 `POST /api/media/lookup`，但用户明确"一时半会不会部署新版本"—— WhatShot 每轮同步的追剧反查会对旧版服务 404，若不处理则**每轮同步重复一条 warning 噪声**，且用户无法分辨"真故障"与"等部署"。
- **最终方案**（SyncEngine.lookupWatchlist 的 catch 分支）：
  ```swift
  } catch {
    // 404 = 部署的 WhatsNew 版本尚无 lookup 端点：静默降级（部署新版后自动生效），
    // 不作为每轮重复的 warning；其他失败如实 warning
    if let whatsnewError = error as? WhatsNewClient.WhatsNewError,
       whatsnewError.message.contains("HTTP 404") {
      continue
    }
    anyFailed = true
  }
  ```
  分批调用时单批 404 `continue` 跳过，另一批照常处理。
- **为什么这样做**：404 在此语境下是**确定性的版本信号**（端点不存在 = 部署版本未含此功能），与"网络抖动/服务挂了"（瞬时，值得报警重试）语义不同。把"等部署"当 warning 会每轮重复刷屏，训练用户忽略警告——警告的公信力比信息全量更值钱。
- **适用条件**：错误形态必须能**确定性区分**"版本未含该端点"（404）与"暂时故障"（5xx/超时/连接拒绝）。若服务端用 404 表达其他语义（如路径混淆），此模式会吞掉真故障——需确认 404 在该服务上只有"无此路由"一种含义。
- **验证证据**：测试 `lookupWatchlistGracefulWhenEndpointMissing`（stub lookup 404 → summary.warning == nil）+ 全量 117 项通过（2026-09-23，commit 141fa30）。
- **交叉验证**：单 agent 单次（设计推演 + 测试），无多 agent 审查。
- **易错点**：
  - 静默降级的另一面是"功能静默失效"——用户不知道反查没生效。缓解：部署后自动生效（无需配置切换），交接文档显式记录该过渡语义。
  - 降级判定只匹配 404；把 400（请求构造错误）也静默掉会吞掉真 bug。
